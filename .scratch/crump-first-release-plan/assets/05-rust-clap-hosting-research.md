# Rust CLAP Hosting Against Crump's Release Constraints

Research date: 2026-07-23

## Question and baseline

Can current Rust CLAP-hosting libraries satisfy Crump's parameter discovery, automation, state restoration, latency reporting, scanning, GUI handling, failure containment, and reproducibility requirements on the accepted Ubuntu Desktop 26.04 LTS `amd64`, native-PipeWire baseline?

This assessment interprets the conditional CLAP promise in the [product contract](../../../requirements/product-contract.md#external-plugins), the explicit [first-public-release gate](../../../docs/product/first-public-release.md#conditional-capability), and the [native PipeWire baseline](../../../docs/adr/0002-native-pipewire-linux-baseline.md). It does not make the inclusion decision reserved for downstream ticket 19.

## Executive finding

**The protocol and `clack-host` provide enough low-level mechanisms to build all of the requested functional host features except failure containment and deterministic reproducibility, which are not properties a binding can provide. No current Rust library examined provides Crump's complete product contract.** In particular:

- CLAP 1.2.10 has stable host/plugin ABI and stable extensions for parameters, sample-offset events, state streams, latency, GUI, render mode, timers, and POSIX file-descriptor integration. CLAP promises 1.x binary compatibility, not host policy, plugin correctness, state transparency, or deterministic audio ([CLAP README](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/README.md#L23-L35), [version 1.2.10](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/version.h#L10-L41)).
- `clack-host` 0.1.0 plus `clack-extensions` exposes those stable extensions through safe Rust host-side wrappers and models the main/audio-thread lifecycle. It is deliberately low-level; its author says there is no functional higher-level Rust host alternative known to them, calls the project feature-complete but still subject to breaking API changes, and says documentation/examples remain incomplete ([Clack README](https://github.com/prokopyl/clack/blob/f874e858ad576c601367b3038af5088a4e671744/README.md#L3-L26), [development status](https://github.com/prokopyl/clack/blob/f874e858ad576c601367b3038af5088a4e671744/README.md#L61-L68)).
- Loading an external native plugin remains unsafe. Clack explicitly says a non-compliant dynamic plugin can trigger undefined behavior regardless of the safe host implementation and recommends additional process isolation to keep failures from affecting the application ([Clack entry safety contract](https://github.com/prokopyl/clack/blob/f874e858ad576c601367b3038af5088a4e671744/host/src/entry.rs#L48-L62)).
- State is an opaque plugin-defined byte stream. The protocol can round-trip it but cannot make it human-readable, portable between plugin versions, semantically diffable, complete, or deterministically rendered ([CLAP state extension](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/ext/state.h#L6-L34), [stream contract](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/stream.h#L6-L34)).

`clack-host` is therefore a plausible implementation foundation, not release evidence. Crump must add and qualify the scanner, graph/PDC integration, source-to-parameter identity, opaque-state envelope, UI/event-loop adapter, plugin worker process and real-time IPC, crash recovery, and reproducibility policy.

## Library assessment

### `clack-host` and `clack-extensions`

`clack-host` is the only evaluated Rust library that is both current and broad enough to be a credible base. The repository's head at the research date is `f874e858ad576c601367b3038af5088a4e671744` (2026-05-03), and crates.io has one published `clack-host` release, `0.1.0`, under `MIT OR Apache-2.0` ([repository commit](https://github.com/prokopyl/clack/commit/f874e858ad576c601367b3038af5088a4e671744), [crates.io record](https://crates.io/api/v1/crates/clack-host), [license](https://github.com/prokopyl/clack/blob/f874e858ad576c601367b3038af5088a4e671744/README.md#L256-L260)). Its extension crate lists stable wrappers for parameters, state/state-context, latency, GUI, render, timers, POSIX FDs, thread-check, audio/note ports, tail, and related integrations ([feature list](https://github.com/prokopyl/clack/blob/f874e858ad576c601367b3038af5088a4e671744/extensions/Cargo.toml#L29-L87)).

The lifecycle API is a useful fit for a real-time host: the main instance remains on the main thread, activation/allocation occurs there, and a separate audio-processor value is sent to the processing thread ([`clack-host` lifecycle](https://docs.rs/clack-host/0.1.0/clack_host/#plugin-lifecycle)). That type-level separation reduces host misuse, but it does not certify third-party plugin behavior, PipeWire integration, callback allocation bounds, or out-of-process operation.

Maturity risk remains material. The project self-describes as feature-complete but under active refinement with future breaking API changes and incomplete docs/examples, and its first published version is `0.1.0` ([status](https://github.com/prokopyl/clack/blob/f874e858ad576c601367b3038af5088a4e671744/README.md#L61-L68), [publication record](https://crates.io/api/v1/crates/clack-host)). Crump should isolate it behind an internal adapter and pin the exact crate checksum/version; it should not expose Clack types as a stable project or extension API.

One compatibility caveat is visible in the current published stack: Clack 0.1.0 depends on `clap-sys` 0.5.0 ([workspace dependency](https://github.com/prokopyl/clack/blob/f874e858ad576c601367b3038af5088a4e671744/Cargo.toml#L19-L31)), whose published constants identify CLAP 1.2.2 rather than current 1.2.10 ([`clap-sys` 0.5.0 source](https://docs.rs/clap-sys/0.5.0/src/clap_sys/version.rs.html#11-22)). The relevant stable extension layouts assessed here are present, and CLAP promises 1.x ABI compatibility, but Crump must test the exact dependency set rather than assume source parity with the newest headers.

### Alternatives

`clap-sys` 0.5.0 is a credible, maintained low-level binding, not a hosting library. It is `MIT/Apache-2.0`, was published in January 2025, and exposes the C ABI with almost no host abstraction ([crates.io package record](https://crates.io/api/v1/crates/clap-sys), [repository](https://github.com/micahrj/clap-sys)). Building directly on it would make Crump own all unsafe lifetime, function-table, extension, thread, and event-buffer machinery already covered by Clack; no release requirement becomes easier.

The only higher-level-looking alternative found with meaningful repository history, `symdaw/audio-plugin-host`, is not credible for this release gate: its own README says it is work in progress and not intended for production, lists "Finish CLAP implementation," and the repository has no release; it is MPL-2.0 ([README](https://github.com/symdaw/audio-plugin-host/blob/a2cdc7f148522c712c5dc444b6daa4e8b592cead/README.md#L1-L10), [releases](https://api.github.com/repos/symdaw/audio-plugin-host/releases), [license](https://github.com/symdaw/audio-plugin-host/blob/a2cdc7f148522c712c5dc444b6daa4e8b592cead/LICENSE)).

`PoHsuanLai/clap-host` advertises convenient parameter/state/GUI support, but at head `a184159db70a73039d94fb0ae0c4908a72224ed4` it has no crates.io package and its manifest contains an unresolved repository-external path dependency (`tutti-midi`), so it is not a consumable independent release candidate ([README claims](https://github.com/PoHsuanLai/clap-host/blob/a184159db70a73039d94fb0ae0c4908a72224ed4/README.md#L8-L20), [manifest](https://github.com/PoHsuanLai/clap-host/blob/a184159db70a73039d94fb0ae0c4908a72224ed4/Cargo.toml#L1-L20), [crates.io absence](https://crates.io/search?q=clap-host)). It also supplies no process isolation.

NIH-plug is a Rust framework for *creating* CLAP/VST3 plugins and standalone applications, not a general third-party CLAP host; its first-party description and export-oriented README do not expose a host API ([NIH-plug repository](https://github.com/robbert-vdh/nih-plug), [pinned README](https://github.com/robbert-vdh/nih-plug/blob/f36931f7af4646065488a9845d8f8c2f95252c23/README.md)). It is not an alternative for this requirement.

## Linux GUI and event-loop implications

CLAP requires most plugin interaction on one stable OS "main thread," and plugin GUI/timer callbacks share that responsiveness concern. The audio-thread is a symbolic, mutually exclusive real-time role and must avoid allocation, locks, I/O, and waiting ([CLAP thread model](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/ext/thread-check.h#L11-L51)). Crump therefore cannot equate its Ratatui input/render loop, PipeWire process callback, and CLAP main thread without an explicit ownership design.

For an Ubuntu Desktop session using X11, embedding requires a real X11 host window and XEmbed parent, something the terminal does not provide. For a Wayland session, CLAP 1.2.10 explicitly does not support embedding, so only plugin-created floating windows are protocol-standard ([CLAP Linux GUI APIs](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/ext/gui.h#L62-L89)). GUI-capable support would therefore introduce a desktop window/event-loop component despite Crump's terminal-first UI, or constrain supported plugins to headless/TUI-exposed parameters. That product boundary must be explicit in the gate.

The host should also implement timer and POSIX-FD support because plugins can use them to integrate periodic work and asynchronous I/O into the host reactor ([timer extension](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/ext/timer-support.h#L11-L27), [POSIX-FD extension](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/ext/posix-fd-support.h#L5-L45)). Clack wraps both, but selecting `winit`, glib, calloop, or another reactor and safely coordinating it with Ratatui and worker IPC remains Crump work.

## Failure containment architecture

Scanning must be out of process even if active DSP is initially not: descriptor scanning calls arbitrary plugin entry initialization, and malformed native code can crash or hang. The official Rust `clap-validator` follows this model, running tests in separate processes by default so plugin crashes do not take down the validator; its fuzzer is also multi-process ([validator README](https://github.com/free-audio/clap-validator/blob/152b9823e992d782c5c1fd33bca0295478b919aa/README.md#L41-L68)).

Meeting Crump's stronger playback-continuity interpretation requires active plugin DSP outside the core audio-engine process as well. This is an architectural inference from CLAP's in-process pointer ABI and Clack's UB warning, not a facility supplied by either project. A viable prototype must demonstrate at least:

- one or more supervised plugin worker processes, with scanner and DSP crashes distinguishable;
- preallocated shared audio/event memory and bounded lock-free command/response transport;
- a deadline policy that substitutes silence or a declared bypass path without blocking PipeWire's process callback;
- latency accounting that includes plugin-reported samples and any fixed IPC pipeline quantum;
- state checkpoint/replay, worker restart, quarantine after repeated failure, and actionable diagnostics;
- behavior when the worker hangs rather than exits, and when a plugin corrupts its own shared buffers;
- GUI ownership compatible with the worker boundary and the selected X11/Wayland policy.

Process isolation limits blast radius; it is not a security sandbox. The accepted unconfined deb baseline gives a plugin worker the user's filesystem/session privileges unless Crump adds an independently designed sandbox, which is outside what CLAP or Clack supplies.

## Opaque state and reproducibility limits

CLAP deliberately assigns state serialization to the plugin. The resulting bytes may include hidden non-parameter state, but the host receives no schema and cannot verify semantic completeness ([state definition](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/ext/state.h#L6-L17)). Consequently:

- Parameter text plus automation is not a valid substitute for state; the specification explicitly tells hosts not to implement that fallback ([parameter persistence rule](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/ext/params.h#L101-L115)).
- An opaque blob can be byte-stable and content-addressed, but it remains semantically unreadable and cannot participate meaningfully in line-based review. A text manifest can identify and hash the blob; it cannot turn plugin-private state into human-readable authoritative source.
- Exact plugin identification needs more than descriptor ID/version because the ID is only encouraged to be unique and the version is arbitrary text ([descriptor contract](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/plugin.h#L12-L39)). Record a cryptographic digest of the loaded binary and reject or explicitly degrade on mismatch.
- Replaying the same events and state does not require the plugin to emit identical samples. The optional offline mode only communicates scheduling pressure and may be refused; it is not a determinism contract ([render extension](https://github.com/free-audio/clap/blob/195b42a004144fab0b3cf95e9c067187d15365b7/include/clap/ext/render.h#L21-L35)).

The official validator includes a configurable `state-reproducibility-binary` test and can check common plugin bugs, crashes, hangs, and specification violations, but passing a validator is not proof of Crump's audible/digital reproducibility promise ([validator README](https://github.com/free-audio/clap-validator/blob/152b9823e992d782c5c1fd33bca0295478b919aa/README.md#L1-L39), [0.4.1 release](https://github.com/free-audio/clap-validator/releases/tag/0.4.1)). Crump needs its own repeated-render and save/reload corpus on the supported baseline.

## Implications and recommended release gate

This research does not decide whether CLAP ships. It recommends that ticket 19 admit CLAP only if a prototype and written support policy pass all of the following evidence gates on the exact Ubuntu Desktop 26.04 `amd64` baseline:

1. **Dependency gate:** Pin `clack-host`, `clack-extensions`, `clap-sys`, and CLAP header/API expectations. Keep them behind a Crump-owned adapter. Record licenses and demonstrate builds from a clean lockfile.
2. **Qualified corpus gate:** Name exact freely redistributable test plugins and binary digests covering instrument/effect, dynamic parameters, state, latency, GUI/headless, and offline render. Run current official `clap-validator`; a pass is necessary but not sufficient.
3. **Parameter gate:** Discover stable IDs/ranges/flags/text, survive legal rescans/restarts, expose them to the DSL, deliver sample-offset automation, and round-trip plugin GUI gestures into source without hidden durable parameter state.
4. **State gate:** Require state support; atomically save/load opaque bytes; detect dirty state; prove close/reopen audible round trip; diagnose absent, corrupt, oversized, incompatible, and binary-digest-mismatched state. The project format must explicitly label the opaque exception to text readability.
5. **Latency gate:** Demonstrate graph-wide PDC in playback, automation, bypass, master render, and selected stems, including latency changes that require restart and any isolation pipeline latency.
6. **Scanner gate:** Discover specification paths and `CLAP_PATH` recursively in a disposable bounded worker. Prove crash, abort, hang, malformed descriptor, symlink/path, duplicate ID, changed binary, and cache invalidation behavior without affecting playback.
7. **GUI gate:** Declare whether the support contract is parameter-only, X11 embedded, Wayland floating, or a tested subset. Prove main-thread, timer, POSIX-FD, resize, close, worker-crash, and headless behavior without blocking Ratatui or PipeWire. Pin the baseline desktop session protocol rather than saying only "Ubuntu Desktop."
8. **Containment gate:** Kill and hang active plugins under load. The core engine and TUI must remain alive, the PipeWire callback must not wait, output must follow a documented safe fallback, state must be recoverable, and diagnostics must identify the plugin and failure. If active DSP remains in-process, this criterion is not met by Clack's Rust safety.
9. **Reproducibility gate:** For every supported plugin binary, compare repeated unchanged real-time captures and offline master/stem renders under a defined tolerance, across save/reload and worker restart. Record nondeterministic plugins as unsupported or as an explicit, user-visible exception; never infer determinism from state-byte equality.
10. **Performance gate:** Measure callback deadline, xruns, CPU, memory, added IPC quantum, scan startup, state size/time, GUI responsiveness, and crash recovery on the named PipeWire hardware fixture. No plugin call, state I/O, scan, allocation, log, or GUI operation may occur on the PipeWire real-time path except the bounded process exchange proven by the prototype.

Passing these gates would show that a particular Crump host architecture and qualified plugin set meet the release constraints. It would not justify a promise of arbitrary CLAP compatibility.

## Uncertainty

- Ubuntu Desktop 26.04 is fixed, but the existing baseline ADR does not pin an X11 or Wayland desktop session. That changes the protocol-standard GUI options and must be resolved before GUI acceptance.
- No active-DSP process-isolation prototype was evaluated here. Real-time IPC latency, scheduling under stock RTKit, worker grouping, and GUI ownership remain empirical questions.
- Third-party plugin behavior cannot be established from specifications or host libraries. A named plugin/version corpus and redistribution/licensing review are still required.
- `clack-host` is young and API-unstable despite broad extension coverage. Its maintenance trajectory and compatibility with later `clap-sys`/CLAP revisions should be rechecked at dependency freeze.
