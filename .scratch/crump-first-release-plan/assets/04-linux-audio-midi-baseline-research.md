# Supported Linux Audio and MIDI Baseline

Status: Planning research for Wayfinder ticket 04  
Researched: 2026-07-23  
Question: Which Linux distributions, audio APIs or servers, MIDI APIs, device assumptions, packaging constraints, and real-time privileges provide a supportable first-release baseline, and what tradeoffs follow?

## Recommendation

Support one reference configuration for the first public release:

| Dimension | Supported first-release contract |
| --- | --- |
| Distribution | Fully updated Ubuntu Desktop 26.04 LTS on `amd64`, in a local systemd user session. Ubuntu 26.04 LTS receives standard security maintenance through May 2031, and `amd64` is an Ubuntu-supported architecture ([Canonical release cycle](https://ubuntu.com/about/release-cycle)). Crump's own update and support duration remains for the public-release support contract to decide. |
| System audio stack | The distribution packages `pipewire`, `pipewire-audio`, and WirePlumber, with the user PipeWire graph running. Ubuntu 26.04 currently ships PipeWire 1.6.2 and WirePlumber 0.5.13; `pipewire-audio` is the distribution's recommended standard desktop audio set and depends on WirePlumber, the PipeWire PulseAudio service, and the PipeWire ALSA plugin ([PipeWire package](https://packages.ubuntu.com/resolute/pipewire), [audio metapackage](https://packages.ubuntu.com/resolute/pipewire-audio), [WirePlumber package](https://packages.ubuntu.com/resolute/wireplumber)). |
| Audio API contract | Crump is a native PipeWire playback client. It produces one stereo output stream, accepts the server-negotiated sample rate, channel format, and quantum, and reports the selected sink, negotiated format, graph quantum, effective latency, stream state, and xruns. PipeWire streams negotiate formats and buffers and invoke processing for each buffer; an RT process callback must avoid blocking and non-RT-safe operations ([PipeWire stream documentation](https://docs.pipewire.org/page_streams.html)). |
| ALSA and JACK relationship | ALSA is the kernel/device substrate used by PipeWire, not a separately supported Crump PCM backend. JACK is an optional compatibility surface provided by PipeWire, not a required daemon and not Crump's first-release contract. Ubuntu offers `pipewire-jack` as a separate JACK plugin package ([Ubuntu package](https://packages.ubuntu.com/resolute/pipewire-jack)); JACK itself is a synchronous low-latency client/server API with callback processing and 32-bit floating-point audio ([JACK API overview](https://jackaudio.org/api/index.html)). |
| MIDI API contract | MIDI input is through PipeWire control/MIDI ports backed by WirePlumber's ALSA Sequencer bridge. The supported device-level contract is a MIDI 1.0 input port visible to ALSA Sequencer and bridged into PipeWire. PipeWire timestamps MIDI events by sample offset in the graph cycle and its session manager creates ports through the ALSA Sequencer bridge ([PipeWire MIDI design](https://docs.pipewire.org/page_midi.html)). |
| Audio device | One wired, ALSA-supported stereo output device selected through PipeWire. The release acceptance device should be a named, readily available USB audio interface that works with Ubuntu's in-tree ALSA driver without a vendor installer. Built-in analog audio may be a secondary smoke-test device. Bluetooth, HDMI-only output, aggregate devices, network audio, multichannel output, and live capture are outside the reference support contract. ALSA is the Linux kernel sound subsystem, and PipeWire is designed for dynamic device configuration rather than fixed ALSA card indices ([kernel ALSA documentation](https://www.kernel.org/doc/html/latest/sound/alsa-configuration.html)). |
| MIDI device | One named USB MIDI 1.0 keyboard/controller whose note, velocity, pitch-bend, channel pressure, CC knobs/faders, and pads appear through an ALSA Sequencer input port. MPE, MIDI 2.0/UMP, external clock, SysEx workflows, network MIDI, and vendor-specific editor/driver requirements are not promised. ALSA Sequencer provides dynamically connectable clients and ports, subscriptions, scheduling, and timestamps ([ALSA Sequencer reference](https://www.alsa-project.org/alsa-doc/alsa-lib/seq.html)). |
| Initial reference operating point | Validate the reference project first at a 48 kHz graph rate and 256-frame quantum. This is an investigation setting, not yet a guaranteed latency budget: PipeWire defines a graph period as quantum divided by rate, so this setting gives a 5.33 ms graph cycle before device and application buffering ([`pw-top` documentation](https://docs.pipewire.org/page_man_pw-top_1.html)). The later performance ticket must set the final accepted quantum, end-to-end latency, CPU, and xrun budgets. |
| Packaging | Publish an `amd64` Ubuntu `.deb` built for 26.04, dynamically linked against the distribution's glibc and required system audio libraries, with exact runtime dependencies generated by Debian packaging tools. Debian policy requires dynamically linked packages to declare the shared-library packages needed at runtime and describes generating those dependencies with `dpkg-shlibdeps` ([Debian shared-library policy](https://www.debian.org/doc/debian-policy/ch-sharedlibs.html#dependencies-between-the-library-and-other-packages), [dependency generation](https://www.debian.org/doc/debian-policy/ch-sharedlibs.html#generating-dependencies-on-shared-libraries)). |
| Real-time setup | Require the stock PipeWire real-time module, D-Bus user/system buses, and RTKit package; do not require root, a custom kernel, an `audio` group, hand-edited PAM limits, setuid, or `CAP_SYS_NICE`. PipeWire first uses `RLIMIT_RTPRIO` where available and otherwise falls back to the Realtime portal or RTKit ([PipeWire RT module](https://docs.pipewire.org/page_module_rt.html)); Ubuntu 26.04 packages RTKit as its realtime policy and watchdog daemon ([Ubuntu RTKit package](https://packages.ubuntu.com/resolute/rtkit)). |
| Privilege failure | Crump must detect and display whether its audio processing thread actually obtained real-time scheduling. If it did not, Crump may continue in an explicitly degraded mode and recommend a larger quantum, but that run does not satisfy release performance acceptance. It must not silently claim low-latency support or attempt privilege escalation. RTKit limits and watchdogs exist because an unbounded real-time thread can make the system unresponsive ([RTKit design](https://github.com/heftig/rtkit/blob/master/README)); the kernel likewise reserves non-RT CPU time by default to permit recovery from runaway RT work ([kernel RT scheduling documentation](https://docs.kernel.org/scheduler/sched-rt-group.html#default-behaviour)). |

This is deliberately a narrow release gate, not a statement that Crump cannot run elsewhere. Other distributions, architectures, classic JACK, direct ALSA PCM, sandboxed packages, and additional devices can be best-effort until separately qualified.

## Why This Baseline

The product contract requires a documented Linux configuration, MIDI input, uninterrupted local playback, and a native path capable of completing a track. The release evidence also requires measurable callback, underrun, update-latency, and UI-responsiveness results on documented hardware. A single current LTS image, one server model, and named reference devices make those claims reproducible without turning the first release into a distribution and hardware certification program.

Ubuntu 26.04 is preferable to 24.04 for a release planned in 2026 or later. Both are LTS releases, but 26.04 has standard maintenance through May 2031 and includes PipeWire 1.6.2, whereas 24.04 ends standard maintenance in May 2029 and currently carries PipeWire 1.0.5 ([Canonical lifecycle](https://ubuntu.com/about/release-cycle), [26.04 PipeWire](https://packages.ubuntu.com/resolute/pipewire), [24.04 PipeWire](https://packages.ubuntu.com/noble/pipewire)). Choosing 26.04 buys two more years of runway and a much newer audio stack at the cost of less field time than 24.04.

PipeWire is the right supported seam because its stream API covers format negotiation, buffer exchange, graph timing, stream state, and real-time callback behavior ([PipeWire streams](https://docs.pipewire.org/page_streams.html)). It also presents MIDI as sample-offset-timestamped graph events and obtains physical MIDI ports from ALSA Sequencer through the session manager ([PipeWire MIDI](https://docs.pipewire.org/page_midi.html)). This gives Crump one clocked graph for audio and performance input while retaining ALSA's Linux device ecosystem.

JACK remains useful interoperability, but making classic JACK2 the baseline would require users to install, configure, and operate another audio server or to select a replacement `libjack`. PipeWire's JACK package exists precisely as a plugin for JACK applications to output through PipeWire ([Ubuntu `pipewire-jack`](https://packages.ubuntu.com/resolute/pipewire-jack)). Crump does not need JACK to complete its native workflow, so requiring it would add configuration and package-state variance without adding a release-critical capability.

## Options Compared

### Distribution choices

| Option | Advantages | Costs and conclusion |
| --- | --- | --- |
| Ubuntu Desktop 26.04 LTS `amd64` | Current LTS; standard maintenance to May 2031; packaged PipeWire 1.6.2, WirePlumber 0.5.13, RTKit, and a standard PipeWire desktop metapackage ([lifecycle](https://ubuntu.com/about/release-cycle), [packages](https://packages.ubuntu.com/resolute/pipewire-audio)). | Newer and therefore less field-proven than 24.04. **Recommended**, with all release tests pinned to fully updated 26.04 package versions. |
| Ubuntu Desktop 24.04 LTS `amd64` | Mature LTS with standard maintenance to May 2029 and packaged PipeWire 1.0.5 ([lifecycle](https://ubuntu.com/about/release-cycle), [package](https://packages.ubuntu.com/noble/pipewire)). | Shorter remaining runway and materially older PipeWire/WirePlumber stack. Keep as a likely best-effort target, not a release gate. |
| Debian 13 `amd64` | Current Debian stable; Debian recommends stable for production and lists full support to August 2028 followed by LTS to June 2030 ([Debian releases](https://www.debian.org/releases/)). | A credible second qualification target, but adding it now doubles installer, desktop-policy, package-version, and support-matrix work without proving a second product path. Defer until the Ubuntu gate passes. |
| Current Fedora Workstation `x86_64` | Fedora made PipeWire the default unified PulseAudio, JACK, and ALSA routing stack starting with Fedora 34 ([Fedora change record](https://fedoraproject.org/wiki/Changes/DefaultPipeWire)). It is useful for testing newer kernels and PipeWire releases. | Fedora supports a release only until about one month after release `N+2`, producing roughly 13 months of maintenance and frequent mandatory rebasing ([Fedora lifecycle](https://fedoraproject.org/wiki/Fedora_Release_Life_Cycle)). Use in compatibility CI if useful, but not as the sole first-release promise. |

Supporting “Ubuntu-derived distributions” is not equivalent to supporting Ubuntu 26.04. Derivatives can change the kernel, session manager policy, package versions, desktop services, and real-time configuration. They should remain best-effort until tested as their own configurations.

### Audio stack choices

| Option | Advantages | Costs and conclusion |
| --- | --- | --- |
| Native PipeWire client over ALSA devices | One desktop/pro-audio graph; negotiated formats and buffers; state and timing telemetry; RT callback contract; optional routing to other graph clients ([PipeWire streams](https://docs.pipewire.org/page_streams.html)). | Linux-specific implementation work and a dependency on session policy. **Recommended supported contract.** |
| JACK client, normally against PipeWire's JACK implementation | Mature callback/port model designed for synchronous low-latency processing ([JACK API](https://jackaudio.org/api/index.html)); can run on PipeWire through Ubuntu's separate plugin package ([Ubuntu package](https://packages.ubuntu.com/resolute/pipewire-jack)). | Adds an optional package and JACK compatibility layer to the minimum install; behavior can differ between PipeWire-JACK and classic JACK. Keep as a possible implementation/interoperability path only if prototypes prove no contract loss. |
| Classic JACK2 server over ALSA | Established professional-audio topology and explicit server configuration. JACK abstracts hardware and synchronously invokes client callbacks ([JACK API](https://jackaudio.org/api/index.html)). | Separate daemon lifecycle and device/quantum configuration; less integrated with the default desktop stack. Not the baseline. |
| Direct ALSA PCM | Lowest-level Linux device access and no media server. | Crump would own device selection, exclusivity, format conversion, hotplug, and coexistence policy. It would duplicate responsibilities PipeWire already centralizes. Reserve for diagnostics or a future fallback, not a promised backend. |

PulseAudio is not a separate candidate. On the recommended image, `pipewire-audio` installs PipeWire's PulseAudio service for legacy clients ([Ubuntu metapackage](https://packages.ubuntu.com/resolute/pipewire-audio)); Crump has no reason to adopt the less graph-oriented PulseAudio client contract for its native engine.

### MIDI choices

| Option | Advantages | Costs and conclusion |
| --- | --- | --- |
| PipeWire MIDI/control ports backed by ALSA Sequencer | Events carry sample offsets against the graph cycle, and WirePlumber bridges ALSA Sequencer clients/streams into PipeWire ports ([PipeWire MIDI](https://docs.pipewire.org/page_midi.html)). | Requires careful conversion from graph-cycle offsets to Crump's transport timeline and validation of hotplug and identity. **Recommended supported contract.** |
| Direct ALSA Sequencer client | Dynamic clients/ports, subscriptions, immediate or scheduled dispatch, real-time or tick timestamps, and system attach/detach announcements ([ALSA Sequencer](https://www.alsa-project.org/alsa-doc/alsa-lib/seq.html)). | Crump must align a separately delivered timestamp domain with the audio callback and manage reconnects itself. Keep as a contingency requiring an explicit baseline revision if PipeWire MIDI proves deficient, not as a hidden first-release fallback. |
| JACK MIDI | Buffer-local MIDI event API colocated with JACK audio; PipeWire maps JACK MIDI events to its control messages ([PipeWire MIDI JACK section](https://docs.pipewire.org/page_midi.html#jack)). | Would make MIDI depend on the optional JACK compatibility package. Not the minimum contract. |
| ALSA raw MIDI | Direct byte stream suitable for specialized hardware protocols. | Gives up Sequencer routing, subscriptions, and higher-level event/timestamp facilities. Not needed for the first-release MIDI 1.0 performance-input promise. |

## Detailed Supported Contract

### Installation and startup

The documented installation should:

1. Require an interactive Ubuntu Desktop 26.04 `amd64` host with current normal updates, not WSL, a VM, container, remote shell without the user's PipeWire session, or a headless server image.
2. Install a Crump `.deb` and rely on apt for system-library dependencies. Ubuntu describes deb packages as its core format with structured dependency management ([Canonical packaging overview](https://ubuntu.com/about/release-cycle#ubuntu-package-categories)).
3. Require the distribution's `pipewire-audio` and `rtkit` packages. Do not replace distribution configuration files or switch the user's audio server in maintainer scripts.
4. Run a preflight that confirms a reachable PipeWire remote, WirePlumber policy service, output sink, usable MIDI bridge when MIDI is requested, negotiated stream format, and actual RT scheduling status.
5. Save a support bundle containing OS/kernel and package versions, PipeWire/WirePlumber versions, selected node names, negotiated formats, graph rate/quantum, xrun counts, and RT status, excluding project audio or private paths by default. `pw-top` exposes graph rate, quantum, format, load, and xrun/error statistics suitable for cross-checking Crump telemetry ([`pw-top`](https://docs.pipewire.org/page_man_pw-top_1.html)).

### Audio behavior

The baseline promises playback, not live audio capture. Crump should open a stereo PipeWire output and follow the selected default sink unless the user explicitly selects a currently available sink. It must handle server-selected formats rather than requiring exclusive hardware ownership; PipeWire stream connection includes format and buffer negotiation and can autoconnect to a chosen target ([PipeWire streams](https://docs.pipewire.org/page_streams.html#connect)).

The engine's internal DSP format, project sample semantics, resampler, and offline renderer are not dictated by this platform decision. The platform adapter must communicate negotiated rate and quantum changes to the engine at a safe boundary. Device loss, server restart, or format renegotiation must stop or silence output safely, preserve the active project, display a diagnostic, and permit reconnection without restarting the whole application where the prototype proves that feasible.

The reference gate should use a wired USB interface because it gives the test a nameable, replaceable device rather than depending on a particular motherboard codec. This report does not assert that every USB audio device is compatible: the performance and support contracts must select the exact device and capture its vendor/product ID, kernel driver, firmware state, supported rates, and stable node identity.

### MIDI behavior

The first-release MIDI contract covers input needed by the product contract: playing a selected instrument, capturing note input, and mapping common controls. Crump should enumerate PipeWire MIDI input ports, show stable human-readable device and port identity where the stack exposes it, allow explicit connection, display incoming activity, and recover predictably from disconnect/reconnect.

Events entering the audio engine need a graph-cycle sample offset or a documented conversion to the engine timeline. PipeWire's MIDI representation supplies a sample offset against the current graph clock cycle ([PipeWire MIDI design](https://docs.pipewire.org/page_midi.html#design)). ALSA Sequencer supports direct delivery plus scheduled events with real-time or musical tick timestamps, but adopting that separate delivery path would change this baseline and require renewed timing validation ([ALSA event scheduling](https://www.alsa-project.org/alsa-doc/alsa-lib/seq.html#seq_ev_queue)).

Persisted mappings must not store only ephemeral ALSA client numbers or PipeWire object IDs. Defining a durable match key and ambiguity UX is unresolved because the cited APIs expose dynamic clients/ports and object lifetimes; this requires a device-identity prototype with the chosen controller.

### Real-time behavior and fallback

Normal installation should use PipeWire's real-time module and RTKit fallback. The PipeWire module requires a sufficient `RLIMIT_RTPRIO` for direct scheduler access and otherwise tries the Realtime portal or RTKit ([PipeWire RT module](https://docs.pipewire.org/page_module_rt.html)). RTKit is specifically designed to grant `SCHED_RR` to constrained user threads through D-Bus, with limits, `SCHED_RESET_ON_FORK`, authorization, and watchdog demotion ([RTKit README](https://github.com/heftig/rtkit/blob/master/README)).

Crump must not equate “the stream started” with “RT scheduling succeeded.” It should inspect the actual callback-thread scheduling policy and expose it in diagnostics. Linux's RT policies use priorities 1 through 99 and fail with `EPERM` when the caller lacks suitable privilege ([Linux `sched_setscheduler(2)`](https://man7.org/linux/man-pages/man2/sched_setscheduler.2.html)). Exact policy and priority remain an implementation/stack choice; Crump should not compete with PipeWire's driver priority or hard-code an undocumented maximum.

If RT acquisition fails:

- Playback may continue with a prominent degraded-status indicator.
- Crump should advise increasing the PipeWire quantum or repairing the stock RTKit/D-Bus installation, not running Crump as root.
- Xruns and deadline misses must remain visible.
- The run is outside the supported low-latency/reference-performance gate even if it appears to work.
- Offline rendering remains available because it does not depend on real-time deadlines.

An advanced PAM `limits.d`/`audio`-group profile can be investigated later for dedicated workstations. It should not be the default because PipeWire already has portal/RTKit fallbacks, and both RTKit and the kernel explicitly guard against runaway RT workloads making the machine unrecoverable ([PipeWire RT](https://docs.pipewire.org/page_module_rt.html), [RTKit security model](https://github.com/heftig/rtkit/blob/master/README), [kernel warning](https://docs.kernel.org/scheduler/sched-rt-group.html#warning)). A PREEMPT_RT kernel may also be benchmarked later, but it is not required by this baseline.

### Packaging boundaries

The release artifact should be an unconfined distro-native `.deb` for `amd64`. `x86_64-unknown-linux-gnu` is a Rust Tier 1 target with host tools and automated build/test guarantees ([Rust platform support](https://doc.rust-lang.org/rustc/platform-support.html#tier-1-with-host-tools)), but Rust's target status alone does not qualify an OS/audio/device combination; Crump's release tests do.

The `.deb` should declare only libraries and services actually used. The recommended native PipeWire path should not require `pipewire-jack` or a direct ALSA client library merely because PipeWire uses ALSA underneath. Build in a clean 26.04 environment and generate shared-library dependencies rather than bundling alternate copies of PipeWire, ALSA, glibc, or RTKit. Debian's packaging policy uses ELF `SONAME` dependencies and generated package relationships to keep runtime libraries available across upgrades ([Debian shared-library policy](https://www.debian.org/doc/debian-policy/ch-sharedlibs.html)).

Do not make Flatpak, Snap confinement, AppImage, musl-static binaries, or third-party distro repositories part of the first supported release. Flatpak denies host devices and services by default; its `--socket=pulseaudio` permission grants sound output, MIDI, and `/dev/snd`, but that is a distinct sandbox permission and integration surface that needs its own real-time, project-file, extension, and device tests ([Flatpak sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html#standard-permissions)). Canonical likewise distinguishes confined snaps from classic snaps with broad host access ([Canonical package formats](https://ubuntu.com/about/release-cycle#ubuntu-package-categories)). These formats may become distribution channels after their behavior is qualified, not wrappers around an untested support claim.

## Product Contract Versus Implementation Choices

The release should promise observable behavior and environment, not a particular crate.

### Product/platform contract to fix now

- Ubuntu Desktop 26.04 LTS `amd64`, updated, with its packaged PipeWire/WirePlumber/RTKit stack.
- Native PipeWire stereo playback with negotiated format/quantum and explicit device, RT, latency, and xrun diagnostics.
- PipeWire MIDI input ports sourced from the ALSA Sequencer bridge, supporting the stated MIDI 1.0 performance and mapping subset.
- Named wired reference audio and MIDI devices, with no vendor driver installer.
- Distro-native `.deb`; no sandbox and no administrator privilege required at runtime.
- Safe degraded behavior when RT scheduling or devices are unavailable, while excluding degraded runs from release performance acceptance.
- Offline rendering that does not require an audio device or PipeWire server.

### Choices to leave open until prototypes measure them

- Direct `libpipewire`/SPA bindings versus a Rust abstraction that demonstrably preserves stream state, timing, xrun, device, and RT semantics.
- The Rust crates used for PipeWire, ALSA Sequencer, resampling, file formats, and device identity.
- The Rust representation and parser used for PipeWire control/MIDI events, provided it preserves graph-cycle offsets, ordering, port identity, and disconnect state.
- Internal sample type, mix rate, block subdivision, resampler, and how graph quantum maps to engine work blocks.
- Whether optional JACK ports are exposed later for inter-application routing.
- Exact thread policy/priority, memory locking strategy, CPU affinity, and PREEMPT_RT benefit.
- Additional `.deb` architectures. Rust supports `aarch64-unknown-linux-gnu` as Tier 1, but that does not qualify ARM hardware, audio drivers, package builds, or performance ([Rust platform support](https://doc.rust-lang.org/rustc/platform-support.html#tier-1-with-host-tools)).

This separation prevents a library selected during prototyping from becoming a user-facing compatibility promise. A library is acceptable only if it can implement the fixed external contract on the reference image.

## Tradeoffs Accepted

- **Narrower reach for credible support.** Users on Arch, Fedora, Debian, Ubuntu derivatives, ARM, classic JACK, or direct ALSA may be able to run Crump, but the first release does not promise or gate on them.
- **PipeWire policy becomes part of the environment.** Crump gains desktop coexistence, routing, negotiation, and common audio/MIDI timing, but must diagnose behavior controlled partly by WirePlumber and distribution configuration.
- **No direct-ALSA escape hatch.** This simplifies behavior and avoids exclusive-device problems, but a broken user PipeWire session blocks supported real-time playback.
- **A recent LTS instead of the most field-proven LTS.** Ubuntu 26.04 provides support to 2031 and PipeWire 1.6.2, but needs an early soak matrix because it is newer than 24.04 ([Canonical lifecycle](https://ubuntu.com/about/release-cycle), [Ubuntu PipeWire package](https://packages.ubuntu.com/resolute/pipewire)).
- **RTKit convenience with bounded authority.** Stock unprivileged setup is safer and easier to document than broad PAM limits, but RTKit policy may cap priorities and must be verified rather than assumed ([RTKit design](https://github.com/heftig/rtkit/blob/master/README)).
- **One architecture initially.** `amd64` captures the conventional desktop production path and Rust's Tier 1 GNU target, but delays ARM users despite Rust and Ubuntu both supporting ARM64 ([Rust targets](https://doc.rust-lang.org/rustc/platform-support.html#tier-1-with-host-tools), [Ubuntu architectures](https://ubuntu.com/about/release-cycle)).
- **Distro-native packaging over portability bundles.** The `.deb` can express exact library dependencies and integrate with the tested stack, but requires separate work before supporting another distro or sandbox.
- **MIDI 1.0 first.** This covers the product's note capture and control mapping while avoiding unproven UMP/MIDI 2.0 behavior. PipeWire documents active MIDI1/UMP conversion policy changes across recent releases, reinforcing the need not to promise MIDI 2.0 yet ([PipeWire MIDI](https://docs.pipewire.org/page_midi.html#design)).

## Required Follow-up Validation

This research chooses the envelope; it does not establish performance limits. The following work must occur before the baseline can become a release claim:

1. **Clean-image installation:** install the `.deb` and declared dependencies on a fresh Ubuntu Desktop 26.04 `amd64` image; confirm no undocumented package, group, PAM, or config-file step is needed.
2. **Version-soak matrix:** test the GA package set and every supported 26.04 PipeWire/WirePlumber/kernel update used by CI. Decide whether support means all security-updated 26.04 systems or a tested minimum package revision.
3. **Reference hardware selection:** publish exact CPU, RAM, storage, audio interface, MIDI controller, USB topology, firmware, and vendor/product IDs. Test built-in analog audio as a secondary path.
4. **Quantum/rate sweep:** measure 44.1 and 48 kHz at 64, 128, 256, 512, and 1024 frames under the reference project. Record callback worst case, xruns, DSP load, end-to-end MIDI-to-audio latency, UI load, and hot-reload spikes. `pw-top` defines the relevant quantum/rate and xrun counters but does not set Crump's acceptance thresholds ([`pw-top`](https://docs.pipewire.org/page_man_pw-top_1.html)).
5. **RT verification:** prove the callback policy with stock RTKit, then deliberately disable RTKit or D-Bus and verify visible degraded behavior, larger-quantum guidance, safe continued playback, and offline rendering.
6. **Failure matrix:** unplug/replug audio and MIDI devices; change default sink, rate, and quantum; restart PipeWire/WirePlumber; suspend/resume; remove the selected device during playback; and exhaust MIDI event input. Verify safe output, no project-state loss, useful diagnostics, and recovery.
7. **MIDI timing and identity:** quantify jitter and ordering through PipeWire's ALSA bridge; compare direct ALSA Sequencer if needed; determine durable matching across ports, reboots, identical devices, hubs, and reconnects. Confirm every promised MIDI message type on the named controller.
8. **Desktop contention:** run common desktop audio concurrently and verify that notifications, browsers, device profile changes, and other PipeWire clients do not silently change Crump's release settings or cause dangerous output.
9. **Library spike:** compare candidate Rust adapters for direct PipeWire, MIDI control ports, RT-safe callbacks, state/error reporting, and package linkage. Reject abstractions that hide quantum changes, xrun data, device loss, or actual RT status.
10. **Cross-distro reconnaissance:** after the reference gate passes, run non-gating smoke tests on Debian 13 and current Fedora to estimate the cost of the next supported configuration; do not weaken the Ubuntu contract to accommodate them prematurely.

The later performance ticket must turn the initial 48 kHz/256-frame operating point into measured limits or replace it. The later support/release ticket must also define how long Crump tests Ubuntu 26.04 updates, when a successor LTS is added, and how users distinguish “known to run” from “supported.”

## Decision Summary

Adopt Ubuntu Desktop 26.04 LTS `amd64` plus the distribution PipeWire 1.6/WirePlumber/RTKit stack as the sole first-release reference configuration. Treat PipeWire as the audio and clocked-MIDI service contract, ALSA as the underlying Linux device and Sequencer substrate, and JACK as optional interoperability. Ship an unconfined native `.deb`, require one named wired ALSA-supported stereo interface and one named ALSA-Sequencer-visible USB MIDI 1.0 controller, and require successful stock RTKit scheduling for performance acceptance while retaining an explicit non-RT degraded mode.

This baseline is supportable because it is specific enough to reproduce and instrument. Its principal costs are limited distribution/hardware reach, dependence on a recent LTS PipeWire policy stack, and deferred sandbox/JACK/direct-ALSA/ARM support. Those are preferable to an untestable promise of generic Linux compatibility for a release whose defining evidence is reliable native end-to-end music production.
